# 业务流程编排系统设计方案

## 一、需求概述

### 1.1 业务背景
基于现有的工作流引擎，在业务系统（应用系统）建设流程编排组件，用于：
- **业务规则定义**：管理应用系统不同业务与业务规则的绑定关系
- **流程灵活配置**：业务规则关联流程编排配置，实现不同业务流程流转的灵活配置
- **生命周期管理**：流程流转过程匹配事件，按规则触发，实现生命周期流转
- **完整追溯**：流转表记录所有的流转过程

### 1.2 核心目标
- 支持**采购、合同、供应商业务**的能力建设
- 支持**原有商务系统的迁移融合**
- 提供**灵活的流程配置能力**，不同业务场景走不同流程
- 提供**完整的流程追溯能力**

## 二、表设计

### 2.1 业务配置表 (sys_business_config)

**作用**：业务说明书，记录公司有哪些业务需要走流程

| 字段名称 | 字段描述 | 字段类型 | 是否必填 | 说明 |
|---|---|---|---|---|
| id | 主键 | int(11) | 是 | 自增主键 |
| name | 业务名称 | varchar(128) | 是 | 如"采购申请业务" |
| code | 业务编码 | varchar(128) | 是 | 唯一标识，如"BUSINESS_PURCHASE_REQUEST" |
| description | 业务描述 | varchar(512) | 否 | 业务详细描述 |
| business_type | 业务类型 | varchar(64) | 是 | contract/purchase/supplier/other |
| business_category | 业务分类 | varchar(64) | 否 | template/workflow/config |
| rule_engine_config_id | 规则引擎配置ID | varchar(128) | 否 | 外部规则引擎配置标识 |
| rule_engine_type | 规则引擎类型 | varchar(64) | 否 | drools/aviator/groovy |
| workflow_enabled | 是否启用工作流 | boolean | 是 | 默认TRUE |
| create_user_id | 创建人ID | varchar(128) | 是 | - |
| update_user_id | 更新人ID | varchar(128) | 是 | - |
| create_time | 创建时间 | timestamp | 是 | - |
| update_time | 更新时间 | timestamp | 是 | - |
| status | 业务状态 | varchar(32) | 是 | active/locked/deleted |
| tenant_id | 租户ID | varchar(128) | 否 | 多租户支持 |

**索引**：idx_code(code), idx_type(business_type), idx_tenant(tenant_id)

| create_time | 创建时间 | timestamp | 是 | - |

## 三、表关联关系

```
sys_business_config (业务配置表)
    ↓ (business_config_id)
    ├── sys_business_resource_binding (业务资源关联表)
    │       ↓ (resource_type + resource_id)
    │       └── 外部资源系统（模板/单据/表单/配置）
    │
    ├── sys_process_orchestration_config (流程编排配置表)
    │       ↓ (orchestration_config_id)
    │       └── sys_process_transition_flow (流转日志表)
    │
    └── sys_process_event_config (事件配置表)
            ↓ (event_config_id)
            └── sys_process_transition_flow (流转日志表)
```

### 4.1 场景一：采购生命周期

#### 业务流程
```
采购申请 → 部门审批 → 财务审批 → 采购完成 → 生成采购订单
```

## 五、核心设计亮点

### 5.1 通用性设计

#### ✅ 业务资源关联表支持任意资源类型
- **resource_type** 字段支持：template（模板）、document（单据）、form（表单）、config（配置）
- 无需为每种业务类型新建表
- 新增业务类型只需在配置表中添加记录

#### ✅ 业务配置表去模板化
- 移除硬编码的 `template_id` 字段
- 通过 `business_type` 和 `business_category` 实现业务分类
- 支持 contract/purchase/supplier/other 等多种业务类型

#### ✅ 规则引擎集成
- 通过 `rule_engine_config_id` 直接关联外部规则引擎
- 支持多种规则引擎类型（drools/aviator/groovy）
- 无需新建业务规则表，利用现有规则引擎能力

### 5.2 灵活性设计

#### ✅ 条件化流程流转
- 通过 `condition_expression` 字段实现条件判断
- 支持金额、客户等级、业务类型等多种条件
- 不同条件走不同流程，无需硬编码

#### ✅ 优先级控制
- `priority` 字段控制流程流转优先级
- 支持多条件匹配时的优先级排序
- `binding_priority` 控制资源绑定优先级

### 5.3 可追溯性设计

#### ✅ 完整的流转日志
- 记录每个业务实例的完整流转过程
- 包括来源节点、目标节点、流转类型、流转结果
- 支持审计和问题追溯

#### ✅ 扩展元数据
- `metadata` 字段（JSON格式）支持业务特定的扩展属性
- 无需修改表结构即可支持新业务需求
- 灵活适应不同业务场景

### 5.4 自动化设计

#### ✅ 事件驱动
- 通过事件配置表实现生命周期状态自动变更
- 审批通过后自动通知下一步
- 流程完成后自动生成文档

#### ✅ 处理器配置

## 核心关系

**配置是场景的"操作说明书"**：
- 配置说"金额≤1万走简单流程"，场景就走简单流程
- 配置说"审批通过后通知财务"，场景就自动通知财务
- 配置说"生成采购订单"，场景就自动生成订单

**场景是配置的"实战演练"**：
- 场景走不通，说明配置有问题
- 场景走错了，说明配置规则有问题
- 场景走对了，说明配置正确
