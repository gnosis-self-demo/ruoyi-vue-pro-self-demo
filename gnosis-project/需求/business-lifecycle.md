# 需求背景描述
在系统中可能涉及多个业务，例如：合同、验收、付款。
在这些业务生命周期的流转，主要通过现有的工作流平台驱动，用户的操作驱动。
现在计划通过一个组件，管理起来一个业务的生命周期，主要分为：
（1）入口控制：发起一个业务的入口。入口控制包括数据入口和校验（对于一些业务来说，也可以没有）。
（2）事件执行：业务的生命周期在开始驱动后，主要由系统事件、用户作业、工作流事件等驱动业务的生命周期向下流转或向上退回。
（3）出口控制：定义一个业务生命周期的终态，在生命周期的尾声，控制是否需要和下一业务生命周期衔接以及数据出口的事件消费影响。

# 需求文档

一、入口控制模块（精简保留）
功能点   说明   边界
1.1 业务入口注册   配置业务类型标识、发起权限角色   仅控制“能否发起”，无业务规则校验

1.2 基础数据校验   配置非空/格式等通用校验   排除金额、资质等业务逻辑判断

二、事件执行引擎（核心增强）
功能点   说明   边界控制
2.1 生命周期状态模型   可视化配置状态节点及拓扑关系（支持多分支路径）   仅定义状态名称与连接关系

2.2 事件-状态路由配置   新增核心能力：- 为同一事件配置多条件路由规则- 条件字段仅限事件元数据（如：workflow.action="approve"、workflow.node="legal_review"）- 支持AND/OR组合、优先级排序（首条匹配生效）   
✅ 允许：工作流推送的标准化元数据（操作结果、节点标识）❌ 禁止：引用业务单据字段（金额、供应商等级等）

2.3 工作流事件标准化Adapter   统一解析工作流平台回调，提取预定义元数据字段至标准事件体   输出字段字典：action（approve/reject）、node_id、operator等

2.4 条件路由执行引擎   事件到达时：1. 按优先级匹配条件规则2. 匹配成功则驱动状态流转（向下推进/向上回退）3. 匹配失败记录告警日志   状态变更仅依赖条件匹配结果，无额外逻辑

2.5 路由规则测试沙箱   模拟输入事件元数据，实时预览匹配路径与目标状态   用于配置验证，不触发真实状态变更

三、出口控制模块（保持轻量）
功能点   说明   边界
3.1 终态标识配置   标记生命周期终点状态   无达成条件校验

3.2 下游触发配置   终态达成后，无条件触发下游业务实例创建   衔接逻辑由下游入口控制

3.3 标准事件发布   发布含业务ID、类型、终态标识的轻量事件   无业务数据透传

四、配置治理支撑
功能点   说明
4.1 事件元数据字典   管理预定义事件属性字段（仅含工作流平台标准化字段），供条件配置下拉选择

4.2 路由规则版本管理   配置修改留痕、支持版本对比与回滚

4.3 全链路追踪看板   展示：- 事件接收记录（含元数据快照）- 条件匹配路径高亮- 状态变更流水

4.4 标准API   POST /lifecycle/event（接收事件）、GET /lifecycle/{id}/trace（追踪流转路径）

关键原则重申：  
🔒 条件安全边界：所有流转条件仅基于工作流平台推送的标准化元数据（操作结果、节点标识等），业务规则判断完全由工作流平台或上游系统完成  
🌉 职责清晰：本组件专注“事件→状态”映射编排，业务决策点前置至工作流配置层  
⚙️ 配置即生效：路由规则修改实时生效，无需代码发布，支撑采购/合同/供应商等多业务快速适配  
📌 交付物明确：输出可直接用于开发的配置项清单（状态模型、事件元数据字典、条件路由规则模板）
